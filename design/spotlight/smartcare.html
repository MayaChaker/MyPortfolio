Overview

SmartCare follows how a real visit works: a patient books a time inside the doctor's working hours, the front desk checks them in, the doctor starts and completes the visit and writes the note, and the administration follows the numbers.

I built it from an empty folder: planned the architecture, designed the database, built the React app and the Express API, and deployed it on Vercel, Render and TiDB Cloud.

Features

Patients

  • Book by department, with each doctor's next free times and fee
  • Move or cancel visits, read notes and prescriptions
  • Activate their file with a one-time code

Doctors

  • Today's list, the waiting room and the next patient
  • Visit notes: diagnosis, treatment, prescriptions, follow-up
  • Weekly schedule and a chart for each patient

Front desk

  • A board with every working doctor as a column
  • Check-in, no-shows, and booking for patients
  • Open a new file with a name, mobile and date of birth

Administration

  • Visits, no-show rate and average wait for 7 or 30 days
  • An activity log of who did what and when
  • Staff accounts with a temporary first password

How it's built

A React app (Vite, React Router, Tailwind) on Vercel talks to an Express 5 API on Render, backed by MySQL through Sequelize.

Every route checks the token and the role on the server; hiding a button is never the only protection. The user is reloaded on each request, so a deleted account or a changed role takes effect immediately.

Decisions

Visit status is a state machine
Scheduled, checked in, in progress, completed. The front desk checks in, only the doctor starts and completes, and a no-show can only be marked after the visit's time.
No double booking
The doctor's and the patient's rows stay locked while the slot is checked and the visit saved. I tested it with two requests sent at the same moment.
Medical history is never deleted
A visit is cancelled, not removed, and an account that has visits can't be deleted.
Hospital time, not server time
Dates and "today" follow Beirut time, wherever the server runs.

Testing

102 backend tests on Node's test runner, against a real MySQL database: access per role, booking conflicts, status moves, uploads and sign-in hardening. GitHub Actions runs them on every pull request, and a scheduled workflow resets the demo data every night.
